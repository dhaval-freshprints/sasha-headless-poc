---
name: deal-manager-resolve-deal
description: Identify the existing Fresh Prints deal for an inbound email or SMS using conversation, contact, order and proof evidence. Use when deterministic routing is missing or disputed, including multiple candidate deals; return candidates for review when evidence is insufficient.
---

Use this skill together with the installed sibling `deal-manager-database` skill. Both are supplied in the same package. Read its schema/identifier map before interpreting IDs. Resolve schema-role placeholders from the configured environment; never use them as literal schema names. Read [matching and input details](references/matching_workflow.md) for channel-specific checks and manual fallback SQL. Apply the Deal Manager Agent system prompt's output contract and conservative decision policy.

1. Preserve the original envelope, subject and new message text. Provider IDs are stored in conversation history external IDs; keep them separate from numeric history row IDs. Use a timezone-aware received time when supplied; never substitute the lookup time for a missing email timestamp. For inputs without a received time, use the bounded manual queries in the matching reference. Require time only when chronology distinguishes candidates. Use complete phone numbers or explicit country context. Separate typed references from untyped numbers and quoted historical references.
2. Prepare the collector input JSON. Preserve provenance for every hint: client/account/deal IDs in incoming payloads are candidates, not automatically verified truth. Use `message_id` for provider IDs and `sasha_external_message_id` only for an actual Sasha history value.
3. Run `scripts/collect_evidence.py --env-file /absolute/private/database.env --input /absolute/private/message.json`. The collector resolves the database helper from the sibling skill. Use the same Python environment with the package dependencies installed. It returns candidates, query IDs, primary-key-bearing evidence, warnings and limitations; it does not make a matching decision.
4. Examine every candidate and every warning. For truncated histories, fetch the needed parent or paginate before asserting uniqueness. Inspect exact references, sender identity and prior exchanges. Do not resolve a multi-deal thread or shared contact by choosing the newest deal.
5. If one verified deal has distinguishing message-specific evidence with no material conflict, return `matched`. Otherwise return the appropriate review/no-match/error result with the next useful check. Never write the result back to a DB or send a message as part of this skill.

On-behalf messages: the sender need not exist in FP Users. Search the named person and organization from the body, verify their relationship to the deal, and compare all relevant candidates. A unique corroborated person/organization/deal match can return `matched` without a sender record or the particular conversation history. Do not downgrade solely because the representative is unknown.

Proof clues: read [proof-number and subject lookup paths](references/matching_workflow.md#proof-number-and-subject-lookup-paths) when a message names a proof or contains a revision-request subject. A number labeled “Proof” may be a proof-item ID. A subject may identify a proof by its exact name even when the body has no number. Start with these specific entity clues before broad body searches. A shared internal sender is not a unique client identity, and missing stored art emails do not block an independently verified proof-to-deal match.

Email: query `<operations>.sasha_conversation_history.external_message_id` for a provider ID or reply parent, and `external_thread_id` for prior messages. Filter by `message_type='EMAIL'` and `deleted_at IS NULL`; verify `sender_name`, direction and deal relationships. A thread can span deals, and history does not store mailbox/grant or recipient metadata. Internal and forwarded messages require extra identity or entity evidence.

SMS: use inbound `sender_name` for the sender phone and compare conversation time, thread/provider IDs and verified deal relationships. The collector supports international and national NANP storage variants. History has no recipient phone column, so it cannot prove the receiving business line. Request review when this missing information is decisive. “Yes”, “stop” and emojis have no unique deal meaning without an antecedent. Report opt-out content as context; do not change preferences.

All conversation evidence comes from `sasha_conversation_history`. Generated outbound rows are unsent drafts; do not describe them as delivered correspondence.

When testing, use `--replay` to skip the target's stored association and filter history to before the supplied timestamp. Replay still sees current contact/deal state and is not a complete historical reconstruction. No accuracy claim is justified by retrieving an already stored deal label. Validate with independently reviewed failed-message examples before enabling automatic routing.
